1. Bounds describe functions

Let f(n) and g(n) be nonnegative for sufficiently large integer n, with g(n) positive there. We compare their growth as n increases, ignoring a finite initial range and constant factors.

  • f ∈ O(g): there exist c > 0 and n₀ such that 0 ≤ f(n) ≤ c·g(n) for every n ≥ n₀. This is an upper bound.
  • f ∈ Ω(g): there exist c > 0 and n₀ such that 0 ≤ c·g(n) ≤ f(n) for every n ≥ n₀. This is a lower bound.
  • f ∈ Θ(g): there exist c₁, c₂ > 0 and n₀ such that 0 ≤ c₁·g(n) ≤ f(n) ≤ c₂·g(n) for every n ≥ n₀. This is a tight bound.

We often write f(n) = O(g(n)) as shorthand for membership in a set of functions; it is not ordinary equality. A tight bound matches the function's order of growth, not its exact value.

One example, several valid statements

For f(n) = 5n + 8 and n ≥ 1, we have 5n ≤ f(n) ≤ 13n. Thus f ∈ Θ(n), using c₁ = 5, c₂ = 13, and n₀ = 1. It is also true that f ∈ O(n²), since 13n ≤ 13n² for n ≥ 1. That upper bound is valid but loose.

For a fixed logarithm base greater than 1, the following functions have strictly increasing asymptotic growth: 1, log n, n, n log n, n², n³, 2ⁿ. Constant factors such as 100n versus n do not change the Θ class. Asymptotic analysis alone does not predict which implementation is faster for a particular small input.

Case analysis comes first

A running time depends on the input, not just its length. First choose the function: best case, worst case, or an expectation under a stated input distribution or algorithmic randomness. Then bound that function with O, Ω, or Θ.

For standard insertion sort on length n ≥ 2, the best-case time is Θ(n) on an already sorted array and the worst-case time is Θ(n²) on a reverse-sorted array with distinct keys. Both functions have upper and lower bounds. O does not mean worst case; Ω does not mean best case.

2. Count calls and combining work

  1. Divide: form smaller subproblems and account for that work.
  2. Conquer: recursively solve the required subproblems.
  3. Combine: construct the full answer from their answers.
  4. Base case: handle small inputs directly; ensure recursion makes progress.

For two equally sized recursive subproblems, a typical recurrence is T(n) = 2T(n/2) + work outside the recursive calls. The outside work includes dividing, combining, and other local operations. The size of a subproblem alone does not determine total time.

Binary search: one surviving half

With constant-time array indexing and index bounds (no copied slices), worst-case binary search follows one half-sized subproblem after constant work: B(n) = B(⌊n/2⌋) + Θ(1) until a constant-size base case. There are Θ(log n) calls, so worst-case time is Θ(log n). A successful search that finds the target at the first midpoint takes Θ(1) time. Binary search is more precisely called decrease-and-conquer: only one smaller problem remains.

Merge sort: solve both halves, then merge

For the standard implementation that merges every pair of sorted halves, assume n = 2ᵏ, n ≥ 1, and a constant-time singleton base case. Then M(n) = 2M(n/2) + Θ(n). The two recursive calls sort both halves. Copying/dividing and merging together take linear work per internal node.

  • At depth d, there are 2ᵈ subproblems of size n/2ᵈ.
  • At each internal level, the total local work is Θ(2ᵈ · n/2ᵈ) = Θ(n).
  • There are log₂ n internal levels and n constant-cost leaves.
  • Total time is Θ(n log n) for n ≥ 2. Non-power-of-two sizes need floors/ceilings but have the same asymptotic bound.

No Master Theorem is needed: count the work per level and how many levels there are. Standard array merge sort also uses O(n) auxiliary storage when its merge buffers are reused across calls; the recursion stack adds O(log n).

Trace a combine step

Merge [1, 4, 9] and [2, 2, 3, 10]. Compare only the two unconsumed heads. The output grows as [1], [1, 2], [1, 2, 2], [1, 2, 2, 3], [1, 2, 2, 3, 4], [1, 2, 2, 3, 4, 9]. The left side is now exhausted; append the right tail [10].

Choose the left head first when values tie. For integer values the two copies look identical; for tagged records this rule preserves their relative order across the left and right halves.

Exercise 1 · Is the bound justified?

Written reasoning · 6 minutes. Let f(n) = 3n² + 2n + 7 for integers n ≥ 1.

  1. For each claim, decide whether it is valid. For a valid upper bound, state whether it is tight: f ∈ O(n²), f ∈ O(n³), f ∈ Ω(n³).
  2. Prove the first claim by giving one suitable pair c and n₀ and an inequality valid for every n ≥ n₀.
  3. A classmate says, “O describes the worst case and Ω describes the best case.” Correct the statement in one or two sentences.
Hint 1 · Compare with the leading term

For n ≥ 1, each constant or linear term can be bounded above by a constant multiple of n². To test a claimed cubic lower bound, consider f(n)/n³ as n grows.

Hint 2 · Name the function being bounded

Ask whether you are discussing the maximum, minimum, or expected runtime over inputs of size n. The notation alone does not choose that function.

Reference explanation · open after attempting

First claim: valid and tight as an upper bound: for n ≥ 1, 3n² ≤ f(n) ≤ 3n² + 2n² + 7n² = 12n². For O(n²), choose c = 12 and n₀ = 1. Together with the lower bound, this gives f ∈ Θ(n²).

Second claim: valid but loose, because f(n) ≤ 12n² ≤ 12n³ for n ≥ 1.

Third claim: false. The ratio f(n)/n³ = 3/n + 2/n² + 7/n³ tends to zero, so it cannot stay at least any fixed c > 0 for all sufficiently large n.

O and Ω are upper and lower growth bounds on whichever function is under discussion. They can bound best-case, worst-case, or expected time; those are separate choices.

Exercise 3 · Implement the combine step

Coding and explanation · 16 minutes. Given two integer arrays left and right, each already sorted in nondecreasing order, return a new sorted array containing every occurrence from both. Do not modify either input and do not use a library sort or merge routine. You only need the merge helper, not a complete merge sort.

  • Each input has 0–100,000 elements. Values are between −1,000,000,000 and 1,000,000,000.
  • Inputs are non-null arrays; in C, NULL is allowed for an input with length zero. Sortedness is guaranteed.
  • The result length is the sum of the input lengths. Duplicates must be retained. Choose from the left input first on equal values.
  • Target: Θ(n+m) time when n+m > 0 and Θ(1) for two empty inputs; O(n+m) output storage and O(1) working space excluding the result. Dynamic-array appends have amortized constant cost.

Hint 1 · Track the unconsumed heads

Use i for the left input and j for the right. Compare heads only while both indices are in range. Append the smaller head and advance only its index. In fixed-size output arrays, also keep output index k.

Hint 2 · Finish the job

The main loop stops as soon as one input is exhausted. Copy the remaining left tail, then the remaining right tail. At most one of these loops will copy anything.

Explain your answer: why is choosing the smaller head safe? Why are no elements lost or duplicated? What happens when one input is empty? Give time, output-space, and extra-working-space bounds.

Reference explanation and code · open after attempting

Invariant: the result contains exactly the consumed prefixes of both inputs, in sorted order; its last element, if any, is no larger than any unconsumed element. Since each input is sorted, the smallest unconsumed value must be one of its heads. Appending the smaller head preserves the invariant, and advancing exactly one index consumes exactly one occurrence.

Each step reduces the total number of unconsumed elements. When one input is exhausted, the other tail is already sorted and can be copied. Thus every occurrence appears once, in order, without writing to either input.

The algorithm writes n+m output values and advances the indices n+m times: Θ(n+m) time for positive total length, Θ(1) if both are empty. It stores n+m result values and only a constant number of indices; output storage is linear, while working space excluding the output is O(1).

Merge reference solutionC
#include <stdlib.h>
// Time: O(n + m). Output: O(n + m). Extra working space: O(1).
int* mergeSorted(const int* left, int leftSize, const int* right, int rightSize, int* returnSize) {
    int total = leftSize + rightSize;
    *returnSize = 0;
    if (total == 0) return NULL;
    int* result = malloc((size_t)total * sizeof(int));
    if (result == NULL) return NULL;
    int i = 0, j = 0, k = 0;
    // Choose the smaller remaining head; choose left on ties.
    while (i < leftSize && j < rightSize) {
        if (left[i] <= right[j]) result[k++] = left[i++];
        else result[k++] = right[j++];
    }
    // Copy either remaining tail.
    while (i < leftSize) result[k++] = left[i++];
    while (j < rightSize) result[k++] = right[j++];
    *returnSize = total;
    return result;
}

def merge_sorted(left: list[int], right: list[int]) -> list[int]:
    result = []
    i = j = 0
    # Choose the smaller remaining head; choose left on ties.
    while i < len(left) and j < len(right):
        if left[i] <= right[j]:
            result.append(left[i])
            i += 1
        else:
            result.append(right[j])
            j += 1
    # Copy either remaining tail without changing the inputs.
    while i < len(left):
        result.append(left[i])
        i += 1
    while j < len(right):
        result.append(right[j])
        j += 1
    return result

A. Count iterations, not indentation

Assume integer n ≥ 1, unbounded integer counters, and unit-cost arithmetic for this pseudocode. Give a tight bound on the number of work() calls for each fragment and justify it.

Pseudocode · independent fragments
# A: sequential loops
for i = 1 to n:
    work()
for j = 1 to n:
    work()

# B: triangular nested loops
for i = 1 to n:
    for j = 1 to i:
        work()

# C: doubling counter
k = 1
while k <= n:
    work()
    k = 2 * k
Hint · Write a count before a bound

For B, sum the inner-loop lengths. For C, list k = 1, 2, 4, … and determine the last exponent that stays at most n.

Reference explanation

A calls work 2n times: Θ(n). B calls it n(n+1)/2 times: Θ(n²). C calls it ⌊log₂ n⌋+1 times: Θ(log n) as n grows. Sequential loops add their counts; nested loops require accounting for the actual inner-loop lengths.

B. Same partition procedure, different recursion shape

Assume a conventional two-way quicksort partition places one pivot, costs Θ(n), and excludes the pivot from later recursive calls. All keys are distinct. Compare approximately balanced partitions with repeated splits of sizes 0 and n−1. Sketch the recursion shapes and explain the total work. This model is not the three-way duplicate-aware implementation from Recitation 1.

Hint · Compare levels with a chain

Balanced partitions give logarithmic depth and linear total partition work per early level. A 0 and n−1 split gives one long chain with shrinking partition costs.

Reference explanation

Balanced splits give Θ(n log n) time. Repeated 0 and n−1 splits give Q(n) = Q(n−1) + Θ(n); summing the shrinking linear costs gives Θ(n²). These are particular recursion shapes, not an average-case proof. For distinct keys and uniformly random pivots, the expected time is Θ(n log n), but the worst case remains Θ(n²).

Discussion and exit check

Compare the growth arguments in Exercise 1 and the level accounting in Exercise 2. Then diagnose this proposed merge shortcut: “When either input ends, return the output immediately.” Use left = [1], right = [2, 3] to show what is lost, and explain which loop repairs it.

Exit check: why is “the array is halved, so the algorithm takes O(log n) time” insufficient? Your explanation should name both the number of recursive calls and the work outside them. Explain which running-time case you are discussing.

Discussion notes

The shortcut returns only [1], losing [2, 3]; copying the remaining right tail repairs this case, and a symmetric loop handles the left tail. Halving describes the length of one chain, not the work across all chains: binary search follows one constant-work child; merge sort solves two children and merges their results. Their worst-case time bounds differ accordingly.
