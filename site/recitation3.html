1. A common path for DP problems

Dynamic programming applies when an optimal answer is built from optimal answers to smaller subproblems (optimal substructure) and the same subproblems come up again and again (overlapping subproblems). Plain recursion re-solves those shared subproblems; DP solves each one once and stores the result.

  1. Define the subproblem. Say in words what OPT(i, j) means and which indices it uses. If you cannot say it in one sentence, the state is not clear yet.
  2. Write the key math function. Express OPT for one state in terms of smaller states by trying every possibility for one decision, usually the first or the last one.
  3. Fix the base cases and the fill order. Use top-down recursion with memoization, or fill a table bottom-up so that every value a cell depends on is already computed.
  4. Find and recover the answer. Name the cell that holds the final answer. To return the solution itself, not just its value, store or retrace the choice made at each cell.
  5. Count the cost. Time ≈ (number of states) × (work per state); space ≈ the size of the table.

Worked anchor: Matrix Chain Multiplication

Matrix Ak has dimensions pk−1 × pk. Multiplying a p × q matrix by a q × r matrix costs pqr scalar multiplications. We want the parenthesization of A1A2⋯An with the fewest multiplications.

  1. Subproblem: m[i][j] = minimum cost to compute Ai⋯Aj.
  2. Key math function: the last multiplication splits the chain at some k, so m[i][j] = min over i ≤ k < j of ( m[i][k] + m[k+1][j] + p(i−1)·p(k)·p(j) ).
  3. Base case and order: m[i][i] = 0. Fill by increasing chain length j − i, because every split uses strictly shorter chains.
  4. Answer: m[1][n]. To recover the parenthesization, store the best split s[i][j] for each cell.
  5. Cost: Θ(n²) states × O(n) choices of k = Θ(n³) time, and Θ(n²) space.

Example: p = (10, 30, 5, 60). Computing (A1A2)A3 costs 10·30·5 + 10·5·60 = 4,500, while A1(A2A3) costs 30·5·60 + 10·30·60 = 27,000. So m[1][3] = 4,500, with split k = 2. Plain recursion tries every parenthesization, and their number grows exponentially. The DP table has only Θ(n²) distinct subproblems.

Sum of Products from lecture follows the same five steps. When you meet a new DP problem, write each step down explicitly before coding. Most DP bugs come from a vague subproblem definition or a fill order that reads cells before they are filled.

2. Why greedy, and when it is right

A greedy algorithm makes one locally best choice at each step and never revisits it. There is no table of subproblems: often it is just a sort followed by one scan, so it is simpler and faster than DP. The price is that a locally best choice is not automatically globally optimal. Every greedy algorithm needs a proof.

Four ways to prove a greedy algorithm correct

  1. Exchange argument (the most reusable). Take an optimal solution OPT and the first greedy choice g. If OPT already contains g, move on to the rest of the problem. Otherwise, find an element o of OPT that g can replace, and check two things: the new solution is still feasible (valid), and its value is no worse. So some optimal solution contains g. You will write one in Exercise 1; Huffman coding in the Extra section uses the same idea.
  2. Greedy stays ahead. Choose a measure of progress and prove by induction that greedy is never behind OPT. In Activity Selection, if gi and oi are the i-th activities chosen by greedy and by OPT, then finish(gi) ≤ finish(oi) for every i, so greedy always has at least as much room left and picks at least as many activities. Caution: being ahead in some measure proves nothing unless that measure implies the final objective.
  3. Greedy choice + optimal substructure, by induction. This is the overall frame. The greedy-choice property says some optimal solution contains the current greedy choice (usually shown with an exchange). Optimal substructure says that solving the remaining subproblem optimally then gives an optimal solution to the whole problem. Induction on the number of choices finishes the proof.
  4. Cut property (coming up with minimum spanning trees in Week 4). For any way of splitting the vertices into two sides that no chosen edge crosses, a lightest edge between the two sides is safe to add. Kruskal's and Prim's algorithms both rely on this.

Coin change: same algorithm, different verdicts

Coin values are 1 = c1 < c2 < ⋯ < cn, with an unlimited supply of each. To pay amount N, choose counts xi ≥ 0 with Σ xici = N that minimize the number of coins Σ xi. Greedy repeatedly takes the largest coin that fits.

Proving a coin system works: bound the smaller coins

One recipe proves every greedy-optimal coin system below. Let R be the total value of all coins smaller than the largest coin cn in an optimal solution.

  1. Exchange rules. Each rule replaces some coins by fewer coins of the same total value, so an optimal solution can never contain the group being replaced. This gives upper bounds on the counts of the smaller coins.
  2. Bound R. Use those bounds to show R < cn.
  3. Match greedy. If an optimal solution used fewer than ⌊N / cn⌋ coins of value cn, its smaller coins would have to add up to at least cn, which is impossible. So it uses exactly ⌊N / cn⌋ of them, just like greedy.
  4. Repeat on the remaining amount with the remaining coins (induction).

Divisibility chain. Suppose every coin is a multiple of the previous one: ci+1 = ki·ci with integer ki ≥ 2, as in {1, 2, 4, 8, 16} or {1, 2, 10, 50, 100}. Exchange rule: ki coins of value ci become one coin of value ci+1. So xi ≤ ki − 1, and R ≤ Σ (ki − 1)·ci = Σ (ci+1 − ci) = cn − 1 < cn. The counts work like the digits of a number in a mixed base (binary for powers of two), and greedy computes exactly those digits.

US coins {1, 5, 10, 25}. Here 10 does not divide 25, so the chain argument does not apply, yet the same recipe works. Write x1, x5, x10 for the counts in an optimal solution.

Try-it answer

Exchanges give x1 ≤ 1 (1+1 → 2); x2 ≤ 2 (2+2+2 → 5+1); x2 = 2 ⇒ x1 = 0 (2+2+1 → 5); x5 ≤ 1 (5+5 → 10); x10 ≤ 1 (10+10 → 20); x20 ≤ 2 (20+20+20 → 50+10); x20 = 2 ⇒ x10 = 0 (20+20+10 → 50); x50 ≤ 1 (50+50 → 100).

So the coins below each value add up to less than that value: below 2, at most 1; below 5, at most 4; below 10, at most 5 + 4 = 9; below 20, at most 10 + 9 = 19; below 50, at most 49 (either 40 + 9 with no 10, or 20 + 10 + 9); below 100, at most 50 + 49 = 99. Step 3 of the recipe applies at every coin, so greedy is optimal. The same argument works for the pattern repeated at every power of ten.

Exactly when do three coins work?

For three coins {1, a, b} with 1 < a < b, write b = q·a + r with q = ⌊b / a⌋ and 0 ≤ r < a. Then:

Greedy is optimal ⇔ r = 0 or q + r ≥ a. Equivalently, greedy fails exactly when 0 < r < a − q.

This is a necessary and sufficient condition. The failing direction comes with a counterexample. If 0 < r < a − q, take N = a + b − 1. Since N < 2b, greedy uses one b and then a − 1 ones: a coins in total. But N = (q + 1)·a + (r − 1), which uses q + r < a coins. The other direction (greedy is optimal whenever the condition holds) needs a separate argument, which we do not show here.

A checklist for coin-change questions

  1. Is there a divisibility chain? Then greedy is optimal.
  2. Only three coins? Apply the q + r test.
  3. Looking for a counterexample? Try amounts just above a large coin that several copies of a middle coin can pay, such as a + b − 1.
  4. Proving correctness? Bound the smaller coins with exchange rules, show they add up to less than the next coin, and induct.
  5. No proof in sight? Use DP: C(0) = 0, C(a) = 1 + min over coins c ≤ a of C(a − c), in Θ(amount × number of coin values) time.

For general coin systems there are also known bounds on where the smallest counterexample can lie, and polynomial-time tests of whether greedy always works. They are useful for checking a system by computer, but they do not replace a proof when one is asked for.

Takeaway: whether greedy is correct depends on the structure of the input (here, the coin system), not on the algorithm alone.

Exercise 1 · Scheduling to minimize maximum lateness

Trace, complexity, and a proof · 15 minutes. One machine must process n jobs, one at a time, without interruption. All jobs are available at time 0. Job j takes pj > 0 time units and has due date dj. If job j finishes at time Cj, its lateness is Lj = Cj − dj (negative if it finishes early). The goal is to minimize the maximum lateness Lmax = maxj Lj. In scheduling notation this problem is written 1 || Lmax.

Greedy rule Earliest Due Date (EDD): run the jobs in order of increasing due date.

Pseudocode · EDD
EDD-SCHEDULE(jobs)              // job j has p[j] > 0 and due date d[j]
    order = jobs sorted by d, ascending (ties in any order)
    t = 0
    Lmax = −∞
    for each job j in order:
        t = t + p[j]            // completion time C[j]
        Lmax = max(Lmax, t − d[j])
    return (order, Lmax)

  2. Complexity. Give the time and space of EDD-SCHEDULE for n jobs. Which step dominates?
  3. Correctness. Prove that EDD minimizes Lmax in three steps, listed below.
  • 3.1 Suppose a schedule with no idle time is not in EDD order. Explain why it must contain two adjacent jobs i, j, with i immediately before j and di > dj (an inversion).
  • 3.2 Swap i and j. Show that no other job's lateness changes, and that the new lateness of each of i and j is at most the old Lj.
  • 3.3 Conclude: starting from any optimal schedule, how do you reach an EDD schedule without making Lmax worse?
Hint 1 · What does a swap change?

Let the pair start at time t. Before the swap, Ci = t + pi and Cj = t + pi + pj. After it, j finishes at t + pj and i at t + pi + pj. Jobs before and after the pair keep their completion times.

Hint 2 · Compare with the old lateness of j

After the swap, job i finishes exactly when j used to finish, but i has the later due date. Job j now finishes earlier than before. Compare both new lateness values with Lj = t + pi + pj − dj.

Complexity. Sorting takes Θ(n log n) with a comparison sort; the scan takes Θ(n), so the total is Θ(n log n). Space is Θ(n) for the sorted order; the scan itself uses O(1) extra space.

3.1 Adjacent inversion. If every adjacent pair satisfied di ≤ dj, the whole sequence would already be sorted by due date, i.e. in EDD order. So a non-EDD schedule has an adjacent inversion.

3.2 The swap. Only i and j move, inside the same time window [t, t + pi + pj], so every other job keeps its completion time and lateness. After the swap, L′j = t + pj − dj ≤ t + pi + pj − dj = Lj, and L′i = t + pi + pj − di < t + pi + pj − dj = Lj because di > dj. Both are at most Lj ≤ Lmax, so Lmax does not increase.

3.3 Conclusion. Start from an optimal schedule. Removing idle time only makes jobs finish earlier, so assume there is none. Each swap removes exactly one inversion, so after at most n(n − 1)/2 swaps the schedule is in EDD order, and its Lmax is still optimal. Schedules that differ only in how they order equal due dates have the same Lmax, because the same calculation with di = dj works in both directions. Hence every EDD schedule is optimal. This is the greedy-choice property in action: some optimal schedule runs the earliest-due job first.

Exercise 2 · LCS, Part A: set up the key math function

Written reasoning and a small table · about 10 minutes. A subsequence keeps some characters of a string in their original order; they do not need to be adjacent. For example, "ACE" is a subsequence of "ABCDE". Given strings X = x1⋯xm and Y = y1⋯yn, a longest common subsequence (LCS) is a longest string that is a subsequence of both. Trying all 2m subsequences of X is hopeless for long inputs, so we use the five-step path from Section 1.

  1. Subproblem. Let L(i, j) be the LCS length of the prefixes X[1..i] and Y[1..j]. Which cell holds the final answer?
  2. Last characters match. If xi = yj, write L(i, j) in terms of a smaller subproblem. In one sentence, explain why it is safe to match these two characters with each other.
  3. Last characters differ. If xi ≠ yj, an LCS cannot use both of them as its last character. Which smaller subproblems remain? Write L(i, j).
  4. Base cases and fill order. What are L(0, j) and L(i, 0)? Which neighboring cells does L(i, j) read, and in what order can you fill the table?
  5. Fill the table for X = "ABCB" (rows) and Y = "BDCAB" (columns). Give the LCS length and one LCS.
  6. Cost. How many cells are there, and how much work does each take? Give time and space.
Hint 1 · Think about the last characters

Any common subsequence of X[1..i] and Y[1..j] either uses xi and yj as a matched final pair, or ignores xi, or ignores yj. When xi ≠ yj, the first option is impossible.

Hint 2 · The table shape

Use rows i = 0..4 for "", A, B, C, B and columns j = 0..5 for "", B, D, C, A, B. Row 0 and column 0 are all zeros. Each cell reads only the cell above, the cell to its left, and the diagonal cell above-left.

Reference explanation · open after attempting

1. The answer is L(m, n).

2. If xi = yj: L(i, j) = L(i − 1, j − 1) + 1. Matching is safe because any LCS of the two prefixes can be changed to end with this pair. If it did not end with this character, appending it would give a longer common subsequence. If it ends with the same character from earlier positions, re-match that final character to xi and yj. Removing the pair leaves a common subsequence of X[1..i−1] and Y[1..j−1].

3. If xi ≠ yj: an LCS ignores at least one of them, so L(i, j) = max(L(i − 1, j), L(i, j − 1)).

4. L(0, j) = L(i, 0) = 0, since the empty string has only the empty subsequence. Cell (i, j) reads (i − 1, j − 1), (i − 1, j), and (i, j − 1), so filling row by row, left to right, works.

Hint 1 · Two index systems

Table indices are prefix lengths: row i means the first i characters. The last character of that prefix is a[i − 1] in 0-based string indexing. Most LCS bugs are off-by-one errors between these two systems.

Hint 2 · Walk the table backwards

Start at (m, n). If a[i − 1] == b[j − 1], record the character and move diagonally to (i − 1, j − 1). Otherwise move to whichever of (i − 1, j) and (i, j − 1) holds the larger value; on a tie, either works. Stop when i or j reaches 0. You collect characters from the end, so reverse at the end or fill an output buffer from the back.

Traceback correctness. Each step follows a case of the key math function that gives the current cell its value. A diagonal step happens only when the characters match, and it lowers the value by exactly 1 while recording one character. A step up or left moves to a neighbor with the same value. The walk therefore records exactly L(m, n) characters. They appear at strictly decreasing positions in both strings, so once reversed they form a common subsequence of maximum length.

Cost. Filling the table takes Θ(mn) time and Θ(mn) space. The traceback takes O(m + n) steps, and the output has O(min(m, n)) characters.

Why two rows are not enough. Two rows give L(m, n) in O(min(m, n)) space, but the traceback has to revisit earlier rows to decide which way to move, so returning the string needs the full table. Getting the string in linear space is possible with a divide-and-conquer method (Hirschberg's algorithm), which is beyond this course.

char* longestCommonSubsequence(const char* a, const char* b) {
    int m = (int)strlen(a), n = (int)strlen(b);
    int cols = n + 1;
    // L[i * cols + j] = LCS length of a's first i and b's first j characters.
    int* L = calloc((size_t)(m + 1) * (size_t)cols, sizeof(int));
    if (L == NULL) return NULL;
    for (int i = 1; i <= m; i++) {
        for (int j = 1; j <= n; j++) {
            // Key math function: match the last characters, or drop one of them.
            if (a[i - 1] == b[j - 1]) {
                L[i * cols + j] = L[(i - 1) * cols + (j - 1)] + 1;
            } else {
                int up = L[(i - 1) * cols + j], left = L[i * cols + (j - 1)];
                L[i * cols + j] = up >= left ? up : left;
            }
        }
    }
    int k = L[m * cols + n];
    char* result = malloc((size_t)k + 1);
    if (result == NULL) {
        free(L);
        return NULL;
    }
    result[k] = '\0';
    // Trace back from (m, n), filling the result from the back; prefer up on ties.
    int i = m, j = n;
    while (i > 0 && j > 0) {
        if (a[i - 1] == b[j - 1]) {
            result[--k] = a[i - 1];
            i--;
            j--;
        } else if (L[(i - 1) * cols + j] >= L[i * cols + (j - 1)]) {
            i--;
        } else {
            j--;
        }
    }
    free(L);
    return result;
}

Optional extra content

This section is provided by the TA for students who want to go further. It is not covered in lectures or on the final exam, and the core exercises do not depend on it. It applies the greedy and exchange-argument ideas from this session to a classic data-compression algorithm.

Why we need it

Text is stored as bits. A fixed-length code gives every symbol the same number of bits: 6 distinct symbols need ⌈log2 6⌉ = 3 bits each. Real data is skewed, though: in English text, e is far more common than z. A variable-length code gives frequent symbols short codewords and rare symbols long ones, which reduces the total number of bits.

Variable lengths raise a decoding problem. With a = 0, b = 1, c = 01, the bits 01 could mean "ab" or "c". A prefix-free code avoids this: no codeword is a prefix of another, so a decoder can read bits left to right and output a symbol as soon as the bits read so far match a codeword.

A prefix-free binary code is equivalent to a binary tree with the symbols at its leaves: going left adds a 0, going right adds a 1, and a symbol's codeword is the path from the root to its leaf. Leaves never lie on another leaf's path, which is exactly the prefix-free property. If symbol c appears f(c) times, the encoded length is B(T) = Σ f(c) · depth(c). Huffman's algorithm finds a tree that minimizes B(T).

How it works: merge the two rarest

Start with each symbol as a one-node tree weighted by its frequency. Repeatedly remove the two lightest trees, make them the children of a new node whose weight is their sum, and put the new tree back. After n − 1 merges a single tree remains. A min-priority queue (binary heap) finds the two lightest trees quickly.

Pseudocode · Huffman codes
HUFFMAN(freq[0..n−1])                    // leaves are nodes 0..n−1
    if n = 1: return ["0"]
    Q = min-priority queue of nodes 0..n−1, keyed by weight = freq
    for node = n to 2n − 2:              // n − 1 merges
        x = EXTRACT-MIN(Q)
        y = EXTRACT-MIN(Q)
        left[node] = x;  right[node] = y
        weight[node] = weight[x] + weight[y]
        INSERT(Q, node)
    // node 2n − 2 is the root; every child was created before its parent
    code[2n − 2] = ""
    for node = 2n − 2 down to n:
        code[left[node]]  = code[node] + "0"
        code[right[node]] = code[node] + "1"
    return code[0..n−1]

Why the greedy choice is safe (sketch)

  1. Exchange step. In some optimal tree, the two least frequent symbols x and y are sibling leaves at the greatest depth. Take any optimal tree and swap x and y with the two deepest siblings. A rarer symbol moves down and a more frequent one moves up, so B(T) does not increase. This is the same idea as the swap in Exercise 1.
  2. Reduction step. Merging x and y into one symbol z with f(z) = f(x) + f(y) gives a smaller instance, and B(T) = B(T′) + f(x) + f(y). An optimal tree for the smaller instance therefore gives an optimal tree for the original one.

Cost: with a binary heap, building the initial heap takes O(n) time, and each of the n − 1 merges does two extract-min operations and one insert in O(log n) time, so O(n log n) total. Writing the codes takes time proportional to their total length.

Hint 1 · Store the tree in arrays

Number the leaves 0..n−1 and the merged nodes n..2n−2 in creation order. Then you only need left[], right[], and weight[] arrays; no node class is required. The last node created, 2n − 2, is the root.

Hint 2 · Codes without recursion

A parent is always created after its children. Visit nodes from 2n − 2 down to n: by the time you reach a node, its own code is already known, so give its left child that code + "0" and its right child that code + "1".         i = (i - 1) / 2;
    }
}

static int heapPop(MinHeap* h) {
    int top = h->ids[0];
    h->ids[0] = h->ids[--h->size];
    int i = 0;
    for (;;) {
        int l = 2 * i + 1, r = l + 1, s = i;
        if (l < h->size && h->weight[h->ids[l]] < h->weight[h->ids[s]]) s = l;
        if (r < h->size && h->weight[h->ids[r]] < h->weight[h->ids[s]]) s = r;
        if (s == i) return top;
        heapSwap(h, i, s);
        i = s;
    }
}

// Time: O(n log n) to build the tree, plus the total code length to write codes.
// Space: O(n) nodes and heap entries, plus the returned code strings.
char** huffmanCodes(const int* freq, int n) {
    char** codes = calloc((size_t)n, sizeof(char*));
    if (codes == NULL) return NULL;
    if (n == 1) {
        codes[0] = malloc(2);
        if (codes[0] == NULL) {
            free(codes);
            return NULL;
        }
        strcpy(codes[0], "0");
        return codes;
    }
    // Nodes 0..n-1 are leaves (symbols); nodes n..2n-2 are merged internal nodes.
    int total = 2 * n - 1;
    long long* weight = malloc((size_t)total * sizeof(long long));
    int* parent = malloc((size_t)total * sizeof(int));
    int* depth = malloc((size_t)total * sizeof(int));
    char* bit = malloc((size_t)total);  // '0' for a left child, '1' for a right child
    int* ids = malloc((size_t)n * sizeof(int));
    if (weight == NULL || parent == NULL || depth == NULL || bit == NULL || ids == NULL) goto fail;
    MinHeap heap = {ids, 0, weight};
    for (int i = 0; i < n; i++) {
        weight[i] = freq[i];
        heapPush(&heap, i);
    }
    // Greedy step: merge the two lightest trees, n - 1 times.
    for (int node = n; node < total; node++) {
        int a = heapPop(&heap), b = heapPop(&heap);
        weight[node] = weight[a] + weight[b];
        parent[a] = node;
        parent[b] = node;
        bit[a] = '0';
        bit[b] = '1';
        heapPush(&heap, node);
    }
    // Parents are created after children, so walk from the root downwards.
    depth[total - 1] = 0;
    for (int node = total - 2; node >= 0; node--) depth[node] = depth[parent[node]] + 1;
    // Each leaf's code is the path of bits from the root; write it from the back.
    for (int i = 0; i < n; i++) {
        codes[i] = malloc((size_t)depth[i] + 1);
        if (codes[i] == NULL) goto fail;
        codes[i][depth[i]] = '\0';
        int v = i;
        for (int k = depth[i] - 1; k >= 0; k--) {
            codes[i][k] = bit[v];
            v = parent[v];
        }
    }
    free(weight); free(parent); free(depth); free(bit); free(ids);
    return codes;
fail:
    for (int i = 0; i < n; i++) free(codes[i]);
    free(codes);
    free(weight); free(parent); free(depth); free(bit); free(ids);
    return NULL;
}

def huffman_codes(freq: list[int]) -> list[str]:

        code[left[node]] = code[node] + "0"
        code[right[node]] = code[node] + "1"
    return code[:n]

// Provided helper: a binary min-heap of [weight, node] pairs.
class MinHeap {
    constructor() { this.items = []; }
    get size() { return this.items.length; }
    push(item) {
        const a = this.items;
        a.push(item);
        let i = a.length - 1;
        while (i > 0 && a[(i - 1) >> 1][0] > a[i][0]) {
            [a[i], a[(i - 1) >> 1]] = [a[(i - 1) >> 1], a[i]];
            i = (i - 1) >> 1;
        }
    }
    pop() {
        const a = this.items, top = a[0], last = a.pop();
        if (a.length > 0) {
            a[0] = last;
            let i = 0;
            for (;;) {
                const l = 2 * i + 1, r = l + 1;
                let s = i;
                if (l < a.length && a[l][0] < a[s][0]) s = l;
                if (r < a.length && a[r][0] < a[s][0]) s = r;
                if (s === i) break;
                [a[i], a[s]] = [a[s], a[i]];
                i = s;
            }
        }
        return top;
    }
}

// Time: O(n log n) to build the tree, plus the total code length to write codes.
// Space: O(n) nodes and heap entries, plus the returned code strings.
function huffmanCodes(freq) {
    const n = freq.length;
    if (n === 1) return ['0'];
    // Nodes 0..n-1 are leaves (symbols); nodes n..2n-2 are merged internal nodes.
    const left = new Array(2 * n - 1).fill(-1), right = new Array(2 * n - 1).fill(-1);
    const heap = new MinHeap();
    for (let i = 0; i < n; i++) heap.push([freq[i], i]);
    // Greedy step: merge the two lightest trees, n - 1 times.
    for (let node = n; node < 2 * n - 1; node++) {
        const [w1, a] = heap.pop();
        const [w2, b] = heap.pop();
        left[node] = a;
        right[node] = b;
        heap.push([w1 + w2, node]);
    }
    // Children are created before parents, so walk from the root downwards.
    const code = new Array(2 * n - 1).fill('');
    for (let node = 2 * n - 2; node >= n; node--) {
        code[left[node]] = code[node] + '0';
        code[right[node]] = code[node] + '1';
    }
    return code.slice(0, n);
}
